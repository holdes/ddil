The one rule of this program

Every number, model name and capability that an SA states in front of a customer must be true of the kit in the room. Several screens show figures that are hardcoded or simulated. This guide names each one and gives the sentence to use instead. An SA who follows the "What to say" column never has to retract a claim.

00 · SA training guidePurpose of the kit
Why the kit exists

Search and generative AI where the network is not.

The DDIL kit runs Elasticsearch, embedding models and a 120-billion-parameter language model on two local machines. It answers questions over local data with no cloud service in the request path. That is the sovereign AI story: the data, the models and the answers stay on hardware the operator controls.

DDIL, defined

Disconnected. No route to the internet or a parent network.

Denied. The network exists but the adversary or the policy blocks it.

Intermittent. Links come and go. Work must continue between windows.

Limited bandwidth. A link exists but cannot carry bulk data or model traffic.

What runs on the kit
  • One Elasticsearch cluster, ddil-vineyard, with a GPU node on the DGX Spark and a CPU node on the Framework Desktop.
  • NVIDIA Nemotron 3.5 Lightning, an open-weight NeMo model, on vLLM on the DGX Spark.
  • Jina Embeddings v5 Omni (Elastic) for text and images, on the DGX Spark.
  • Kibana with Agent Builder, the demo backend and the demo frontend on the Framework Desktop.

Pre-show check before every show

Confirm the kit config points at Nemotron 3.5 Lightning and Jina v5 Omni, and that all nodes and Kibana run 9.5.6 with matched security settings. Runbook 02 shows how.

What a customer should leave with

  • Elasticsearch, vector search, an LLM and an agent framework run on hardware that fits in a case and needs no external network at run time.
  • The same Elastic platform features used in the cloud (kNN and hybrid retrieval, inference endpoints, Agent Builder with ES|QL tools) work on the edge kit.
  • The SA was precise about what was measured on the kit and what was illustrative.

00 · SA training guideLearning path
Learning path

Four levels. Sign-off at each one.

An SA moves up one level at a time. A certified presenter signs off each level against the checklist on the next page. Level 3 and Level 4 require time on the physical kit.

Level 1 · Observe

Goal. Know the story, the hardware and the honesty rules.

  • Read this guide and the Architecture guide (01).
  • Watch a certified presenter run all three adventures end to end, including a reset.
  • Study the live and staged tables on pages 6 to 8 until each "What to say" line is familiar.
  • Read the three scenario runbooks (03, 04, 05).
Level 2 · Rehearse in the mock

Goal. Run every click path and every line without the kit.

  • Open mock/index.html from disk. It is plain HTML with no backend and runs scripted versions of all three adventures with a presenter coach.
  • Run each click path from runbooks 03 to 05 against the clock.
  • Practise the staged-element lines aloud until they sound natural.
  • Record one full rehearsal and review it with a peer.
Level 3 · Run on the kit with a shadow

Goal. Operate the real kit with a certified SA present.

  • Power on and bring up both nodes with runbook 02.
  • Run every pre-show health check and interpret each result.
  • Present each adventure once while the shadow observes.
  • Recover from at least one failure the shadow injects, such as a stopped Jina server or a cold model.
  • Reset between adventures and shut the kit down.
Level 4 · Solo

Goal. Run customer sessions alone.

  • Run the kit for a customer session with no shadow.
  • Complete the pre-show checklist from the quick reference card (06) before every session.
  • Log any new failure, its symptom and the recovery used, and send it to the kit owner.
  • Re-certify after any merge that changes a screen, a model or a number listed in FACTS.md.

Rules that apply at every level

  • Use FACTS.md for any figure that is not in these documents. If FACTS.md does not contain it, do not state it.
  • Treat any number on a screen tagged Staged as illustrative, and say so out loud before the audience reads it.
  • When a fallback might be on screen, check the backend directly before the session (runbook 02, health checks).
00 · SA training guideSign-off checklists
Sign-off

What the certifier checks at each level.

The certifier ticks each item only after seeing the SA do it or explain it unprompted. Record the date, the kit, and the certifier's name on the sign-off sheet held by the kit owner.

Level 1 · Observe
  • Explains DDIL and the sovereign AI purpose of the kit in two minutes.
  • Names both nodes, their IP addresses and what each one runs.
  • States which adventure uses Agent Builder and which does not.
  • Explains that the indexing race is a timed simulation.
  • Explains that Need-to-Know uses an application-side filter and not native ES document level security.
  • Lists the screens that can silently show canned data.
Level 2 · Rehearse
  • Completes each click path in the mock within its suggested time.
  • Delivers the staged-element line at each staged screen without notes.
  • Uses the exact suggested prompts from the runbooks.
  • Answers five likely questions from runbooks 03 to 05 accurately.
  • Describes the reset for each adventure.
  • Recorded rehearsal reviewed by a peer.
Level 3 · Kit with shadow
  • Brings up the Spark and the Framework in the documented order.
  • Runs the health checks and confirms both ES nodes, vLLM and Ollama, the Jina server, Kibana and the backend.
  • Confirms the backend is not serving fallback data.
  • Confirms 9.5.6 on every node and the config on Nemotron 3.5 Lightning and Jina v5 Omni.
  • Warms Nemotron 3.5 Lightning before the first audience question.
  • Recovers from an injected failure with the troubleshooting table.
  • Resets and shuts down cleanly. Never runs docker compose down -v by habit.
Level 4 · Solo
  • Two shadowed customer sessions completed without certifier intervention.
  • One full session run solo with a post-session debrief.
  • Pre-show checklist completed and filed for each session.
  • Knows the known issues as of 13 Nov 2026 (runbook 02) and how each one shows on stage.

00 · SA training guidePresenting honestly
Presenting honestly

Say what is true before the audience asks.

Technical audiences find staged numbers. When the SA labels a simulation first, the live parts gain credibility. When the audience finds it first, the live parts lose it.

Five habits

  1. Label before the reveal. Say "this is a timed simulation" before the race starts.
  2. Point at the live proof. In the live screens, point to the measured value: took_ms on SEC search, the visible-document count on Need-to-Know, the phase timeline in the AI Agronomist.
  3. Name the model that is running. NVIDIA Nemotron 3.5 Lightning on vLLM and Jina Embeddings v5 Omni on the local server, both on the DGX Spark. Ignore model names printed on canned panels.
  4. Skip the dead screens. Search, Crop Health and System add risk and no proof.
  5. Never quote a speedup or TCO percentage from the kit screens. Refer the customer to Elastic's published GPU indexing material and offer a follow-up.
